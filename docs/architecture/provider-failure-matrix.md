# Provider failure matrix

What Nivomi does when each dependency fails. **Built** rows are implemented and tested; **Design**
rows are the required behaviour for components that do not exist yet, and become acceptance
criteria for their stories.

| Dependency                         | Failure                                       | Detection                                                                           | User-visible behaviour                                                                | System behaviour                                                                                          | Status                                   | Evidence                                            |
| ---------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------- |
| PostgreSQL                         | Unreachable, restarting, too many connections | Query errors classified by `isDatabaseUnavailable`; readiness ping with 2 s timeout | `503 DATABASE_ERROR` / `DEPENDENCY_UNAVAILABLE`, retryable, generic message           | Liveness stays up (the task is not killed); readiness fails so the ALB drains the task; `Retry-After: 5`  | Built                                    | `it/degradation.test.ts`, `database-errors.test.ts` |
| PostgreSQL                         | Slow queries                                  | Pool connection and statement timeouts (`packages/database/src/client.ts`)          | Request fails with a retryable error instead of hanging                               | Worker jobs time out after 30 s and retry with backoff                                                    | Built                                    | `it/jobs.test.ts`                                   |
| Email provider (dev mailbox → SES) | Send fails or times out                       | Job handler throws                                                                  | Nothing: the request already succeeded (`202`)                                        | Job retries with exponential backoff and jitter, up to 5 attempts, then `FAILED` with `last_error`        | Built (dev mailbox); SES adapter pending | `it/jobs.test.ts`                                   |
| Job worker                         | Crash mid-job                                 | Lock older than 5 minutes                                                           | None                                                                                  | Stale lock recovered; job re-run (handlers are idempotent: tokens re-minted, only the newest valid)       | Built                                    | `it/jobs.test.ts` (orphaned job)                    |
| Rate-limit store (memory → Redis)  | Redis unavailable                             | Store call throws                                                                   | Requests continue (design: fail open for the global limit, fail closed for login/OTP) | Alert; per-process memory fallback                                                                        | Design (memory store today cannot fail)  | ADR-019                                             |
| Web → API forwarder (dev/e2e)      | API down                                      | `fetch` error or 30 s timeout                                                       | `503 SERVICE_UNAVAILABLE` envelope, friendly message                                  | —                                                                                                         | Built                                    | `api-forward.test.ts`                               |
| Browser → API                      | Network loss                                  | `fetch` rejects                                                                     | "We could not reach Nivomi…" with retry                                               | Access token refresh is single-flight; retries after a refresh conflict                                   | Built                                    | `client.test.ts`                                    |
| Telephony (Exotel)                 | API error, webhook delay, call drop           | Adapter errors; missing status callbacks past a deadline                            | Call shows "failed" with reason; campaign keeps running                               | Circuit breaker per organization and provider; retry per FR-40 rules; eligibility re-checked at dial time | Design (Phase 4)                         | PRD FR-38–FR-40, FR-59                              |
| STT/TTS (Sarvam)                   | Latency spike, stream failure                 | Turn latency over budget; stream errors                                             | Short filler, then graceful end or fallback voice                                     | Fallback provider/voice per FR-59; incident metric                                                        | Design (Phase 4)                         | PRD FR-55, FR-59                                    |
| LLM                                | Timeout, rate limit, bad output               | Per-call timeout; schema validation of tool calls                                   | Agent uses a safe scripted line and offers a callback                                 | `LLMRouter` fallback model; loop guard; tokens metered even on failure                                    | Design (Phase 4)                         | PRD FR-63, FR-64                                    |
| HubSpot                            | Outage, 429, token revoked                    | HTTP status; OAuth refresh failure                                                  | Integration status "degraded"/"reconnect needed"                                      | Outbox-driven sync retries; CRM failure never fails the business event (FR-95)                            | Design (Phase 7)                         | PRD FR-93–FR-95                                     |
| Razorpay                           | Webhook delay or duplicate                    | Signature + idempotency key                                                         | Payment status "pending" until confirmed                                              | Idempotent webhook handling; daily reconciliation (FR-104)                                                | Design (Phase 8)                         | PRD FR-102, FR-104                                  |
| MSG91 (OTP)                        | Send failure                                  | Provider error                                                                      | "Could not send code, try again" with cooldown                                        | Retry once; rate-limited per number and member                                                            | Design (Phase 9)                         | PRD FR-147                                          |
| S3                                 | Upload/download failure                       | SDK errors                                                                          | Import upload fails with retry; recordings show "unavailable"                         | No public URLs ever; signed, short-lived URLs only                                                        | Design (Phases 2, 4)                     | PRD FR-128, FR-60                                   |

**Rules that apply to every provider:**

- Business logic depends on interfaces, and adapters hold vendor code.
- Timeouts on every call.
- Errors mapped to envelope codes (`PROVIDER_ERROR`, `TIMEOUT`, `DEPENDENCY_UNAVAILABLE`) with
  user-safe messages.
- Credentials never logged.
- Failures metered and alerted (Phase 10).
